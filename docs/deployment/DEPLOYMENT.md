# Local, staging and production setup

Native Windows: Node.js 22, Python 3.13, Git and network access are required. `scripts/Setup.ps1` installs portable PostgreSQL, Redis and Mailpit inside ignored .tools, installs locked npm/Python dependencies, generates secrets, migrates and seeds synthetic users. Run `scripts/Start.ps1` and inspect evidence/health.json. This installation uses frontend 3000, API 4001, analytics 8001, Mailpit 8025. Ports 4000 and 8000 are occupied by unrelated processes and were left untouched. The worker uses 8081 internally for health.

Docker Engine and Compose are installed in Ubuntu WSL using open-source tooling; no Docker Desktop subscription is used. See `docs/deployment/WSL_DOCKER.md`. The original isolated Compose stack and the optional 512 MiB Render demo container have executed browser checks; actual reports are under `evidence/`. The supplied multi-service stack contains web, API, analytics, PostgreSQL, Redis, worker, migration job and Mailpit. PostgreSQL/Redis have no published host ports, the internal network separates the data plane and application services run as non-root users. Use the isolated verification override/different ports when native services are already running; do not reset their database.

Verified free HTTPS demonstration: https://fincore-wallet-demo-nitinsharma.onrender.com . Its optional shared-process deployment, eight public browser checks, secure-cookie/readiness evidence and sleeping/database-expiry limitations are documented in `docs/deployment/RENDER_DEMO.md`. This does not claim a completed always-on production architecture.

Staging/production-like setup uses `docker compose -f docker-compose.yml -f infrastructure/docker/compose.production.yml up --build -d`. Set fresh credentials and NODE_ENV=production; demo seeding is disabled. The API uses secure cookies in production, so HTTPS must be available. Keep the deployment database distinct from fincore_test. Do not expose PostgreSQL/Redis or the internal analytics secret. Do not deploy development demo credentials publicly.

For an always-on VM production deployment, actions remaining include selecting/provisioning an eligible host and domain, an unprivileged deployment account, DNS, certificates, the reverse proxy from infrastructure/nginx/fincore.conf, inbound firewall restrictions to 443 plus controlled SSH, and private data services. Store secrets outside the repository in /opt/fincore/source/.env with mode 600. Configure WEB_ORIGIN and build-time NEXT_PUBLIC_API_URL to the HTTPS domain's /api/v1 route. The proxy template targets host API port 4000; adjust it to the selected host mapping (4001 by default locally).

Install infrastructure/docker/deploy-revision.sh as root-owned /opt/fincore/deploy-revision.sh for that VM target. The checkout lives in /opt/fincore/source. Configure GitHub staging/production environments with DEPLOY_HOST, DEPLOY_USER, DEPLOY_KEY, DEPLOY_KNOWN_HOSTS and HEALTH_URL, required reviewers and branch restrictions. The workflow validates a full commit SHA, uses strict host-key checked SSH and verifies readiness. No approved SSH production deployment is claimed; the free Render demo is verified separately.

For rollback, record the previous immutable commit/image. Read /opt/fincore/previous-revision and invoke the same deployment script with that SHA. Do not automatically run reverse financial migrations. Use additive compatible schema changes; restore encrypted backups into a separate database and verify integrity before any cutover. Never edit/delete posted journal history to repair financial operations.

Backups: `python scripts/recovery.py` creates an encrypted local custom-format PostgreSQL dump using BACKUP_SECRET, AES-256-GCM and scrypt, restores it into a new isolated database, compares journal counts/totals and checks balance invariants, then removes the drill database. Keep encrypted backups and the backup secret in separate secure stores. Target educational RPO is one scheduled backup interval (recommend 24 hours); target RTO is 30 minutes. The measured local drill is in evidence/restore-drill.json and is not a cloud recovery SLA. Offsite backup scheduling and cloud monitoring require the selected host.

Monitoring: GET /health, /ready and /metrics on Express, /health on analytics and worker's private port 8081. Structured financial/security audit records are in PostgreSQL. stdout logs contain request IDs and safe event metadata. Alert on unavailable readiness, failed deliveries, open reconciliation differences, high-risk queues and journal imbalance. Mailpit remains local-only capture; external sandbox adapters require test credentials.
